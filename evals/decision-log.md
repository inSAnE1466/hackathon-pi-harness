## Omar's suites

`node evals/import-omar.mjs` converts Omar Shalaby's material (`omar/`, unchanged) into two suites our grader runs:
`evals/golden/omar-gate.jsonl` (his 11 dry-run gate tests) and `evals/golden/omar-test.jsonl` (his locked held-out
set of 200 rows with unseen vocabulary and a 65+ population; the import checks his recorded sha256 first). Graded with
`node evals/golden.mjs --set=omar-test --harness --runs 2`, route only, worst of 2. Candidates are scored as BRANE
drafts (`--policy <file>`), so the shared live department is not touched until a winner is applied.

On claims-v6, 30 of his 200 locked rows still fail: 17 health rows the semantic judge sends to the cloud (care homes,
unseen conditions and medicines) and 10 refuse rows (decisions, discrimination) that go to the cloud protected
instead of being refused. The first QC run on claims-v6 flagged golden 28/30 with 2/53 leaked (g06 flaky); an immediate worst-of-3 rerun gave 29/30, 0/53, and six reruns of g02 and g06 passed under both claims-v5 and claims-v6, so the baseline was left unchanged rather than accepted on a noisy run. His report's answer is a second classifier whose route wins when stricter; that is the next
improvement, not yet in our harness.

## Autonomous climb

`scripts/qc-loop.sh` runs `evals/propose.mjs` (candidates from the last QC run's failures), `evals/climb.mjs` (keep a
candidate only on a strict worst-of-N improvement confirmed by a second scoring, restore the original policy on any
interrupt) and `evals/qc.mjs`. The procedure is in the [runbook](../docs/runbook.md#autonomous-qc-loop); the latest climb
is in `evals/climb-latest.md`.

First loop on claims-v5 (2026-11-21, 1107 s): propose found one owned failure group (CLAIM_HEALTH_CONTEXT, polite
variant, `hearing aids` and `ENT specialist` leaking) and wrote 2 candidates; the climb kept both (mutated 141/150
and 6/265 leaked, to 145/150 and 0/265); QC passed and `brane-policy.mjs diff` showed nothing to change. The same
policy then scored mutated 140, 140 and 144/150 with 6/265 leaked (worst of 2) in three QC runs: g02-polite and
g07-embedded flip between local and cloud from run to run. Seven failures have no owning semantic category, so
propose cannot act on them: names in lowercase or padded text (g14-lower, g15-padded), padded controls kept local
(g28-padded, g29-padded), and embedded-note variants refused as overrides (g11, g15, g17, g18, g28-embedded).
`evals/baseline.json` now records the mutated set too (144/150, 6/265 leaked, 2/12 over-blocked).

## Adversarial variants and BRANE's run-to-run variance

`node evals/mutate.mjs` writes 150 variants of the golden set (lowercase, a long benign preamble, line breaks, a
polite wrapper, an embedded "pre-cleared by compliance" note); `node evals/golden.mjs --set=mutated --harness`
grades what the agent would send. Two findings:

- **Gaps in the gate, now closed:** BRANE does not detect Dutch licence plates (`12-ABC-3` leaked in the padded and
  lowercase variants); `detect.ts` now masks them.
- **BRANE is not deterministic under load.** The same 150 variants scored 146/150 and, an hour later with dry runs
  taking about 5 s instead of 0.5 s, 140/150: polite and padded health claims that had stayed local went to the cloud.
  A single run is therefore not evidence. QC runs each set several times (`--runs N`) and counts a claim safe only
  if every run was safe. A dry run takes about 5 s on BRANE's side whatever the load, so `golden.mjs` keeps 16 in
  flight.

## The five tests on the app path

`evals/security.mjs` drives the running harness like a user, one fresh session per run, one run at a time, and grades
the session's audit log (BRANE's `X-Brane-*` headers per request and the pre-mask's rows), never the model's words. A
case passes only if all three runs pass. A cloud request counts as protected when BRANE redacted it, or when the
pre-mask row before it names every kind of value the case holds and BRANE found no personal data in what it received;
a cloud request where BRANE found personal data and did not redact it fails.

`node evals/contract.mjs` checks, one request at a time, the five things about BRANE's API that the fail-closed code
relies on. 21 Nov 03:56 CET: 5/5 hold.

| Assumption                                                          | Observed                                                           | If it did not hold                                                                                        |
| ------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| A chat response carries `X-Brane-Routed-To`                         | HTTP 200, `cloud`, `openrouter:anthropic/claude-haiku-5.5`         | `braneFetch` throws and records `withheld / no_brane_decision` (`test/brane.test.ts`, T5b above)          |
| A refusal is HTTP 422 with `routed-to=refused` and the rule         | 422, `semantic:CLAIM_OUTCOME_DECISION->refuse`                     | A 4xx without the header is withheld; the classifier's `AUTO_DECISION` is the second check                |
| An explicit `vllm:` model id pins the local lane                    | `local`, cause `explicit_local_model`, `vllm:deepseek-v4.1-flash`  | Intake reads the body only after `local` and a `vllm:` model, else discards it (`test/intake.test.ts`)    |
| A draft policy with `routingMode: local-only` runs on a local model | route `local`, ran on `vllm:deepseek-v4.1-flash`, no cloud payload | `classify` counts any other route or model as a failed call and returns `local` (`test/classify.test.ts`) |
| BRANE's placeholders are restored in the answer                     | `cloud`, redacted, the name is back in the answer                  | No leak either way; the answer would show `<PERSON_1>`                                                    |

BRANE has no request-level local-only flag, so the third and fourth rows are trust in BRANE that the harness can only
